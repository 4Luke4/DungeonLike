# Contributing to DungeonLike

DungeonLike is proprietary software (see [`LICENSE.md`](LICENSE.md)).
Contributions are accepted from invited collaborators. By opening a pull request
you confirm that you have the right to contribute the change and that you grant
the copyright holder the licence described in `LICENSE.md`.

Read [`CLAUDE.md`](CLAUDE.md) as well: it is the repository's working standard
and it takes precedence over this guide wherever the two overlap.

---

## 1. Verification policy — read this first

**Nothing in this repository is executed locally.** Do not run Gradle tasks,
tests, builds, Android tooling, emulators or packaging commands on your machine
as part of a contribution. Every executable verification happens in GitHub
Actions.

Local work is limited to editing files and to read-only inspection: reading
diffs, checking file modes, and reviewing repository status.

A change is **not** verified until the relevant workflow jobs are green. If a
job could not run, or coverage was deliberately skipped, say so explicitly in
the pull request body instead of leaving it implied.

## 2. Getting set up

```sh
git clone https://github.com/4Luke4/DungeonLike.git
cd DungeonLike
git config commit.template .gitmessage   # required: enables the commit format
```

The System Reference Document PDFs referenced by the localisation guide live in
`srd/`, which is intentionally untracked. Obtain them yourself; never commit
them.

## 3. Branches and pull requests

- Branch from `main`, named `<type>/<short-topic>` using the commit types below,
  for example `feat/loot-tables` or `ci/cache-godot-templates`.
- Keep a pull request to one coherent change. Unrelated cleanup, reformatting of
  untouched files and speculative abstractions will be asked for separately.
- Fill in the pull request template honestly, including the sections that record
  which CI jobs passed and which coverage was skipped.
- Every pull request needs a review from a code owner (see
  [`.github/CODEOWNERS`](.github/CODEOWNERS)) and green required checks.

## 4. Commit messages

Commits follow [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)
exactly as described in [`.gitmessage`](.gitmessage), and the
`Commit messages` workflow enforces it on every pull request.

```sh
<type>[optional scope][!]: <description>

[optional body]

[optional footer(s)]
```

- Allowed types: `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`,
  `refactor`, `revert`, `style`, `test`.
- The description is imperative, starts lower-case, has no trailing full stop,
  and the whole subject line is at most 100 characters.
- A breaking change uses `!` after the type or scope **and** a
  `BREAKING CHANGE:` footer.
- Each commit must make sense on its own. Prefer several small commits over one
  large one.

Pull requests authored by `dependabot[bot]` are exempt from this check, because
their subjects are generated by Dependabot itself.

## 5. Code standards

### Everywhere

- Comment the non-obvious: security boundaries, lifecycle behaviour,
  compatibility decisions, workflow constraints and licensing constraints.
  Never write a comment that only restates the code.
- Never restate a value that already has a source of truth. Android SDK, build
  tools, NDK, ABI and Java versions live in
  [`config/android/toolchain.properties`](config/android/toolchain.properties);
  library and plugin versions live in
  [`gradle/libs.versions.toml`](gradle/libs.versions.toml); the application
  version lives in [`VERSION`](VERSION).
- Do not copy implementations whose licensing or provenance is unclear.

### Kotlin (`app/`, `host-core/`)

- Kotlin official style, 4 spaces, 120 columns; `.editorconfig` is authoritative.
- The host owns platform capability only. Game rules, content and UI belong in
  GDScript. See [`app/CLAUDE.md`](app/CLAUDE.md).
- Anything that can be tested without a device belongs in `:host-core` so that
  CI can unit-test it.

### GDScript (`game/`)

- Follow the official Godot style guide: **tabs** for indentation, `snake_case`
  files and functions, `PascalCase` class names. `gdformat --check` and `gdlint`
  run in CI.
- Typed GDScript everywhere (`var x: int`, `func f() -> void`).
- **Never call `randi()`, `randf()`, `randi_range()`, `randf_range()`,
  `shuffle()` or `RandomNumberGenerator` directly.** All randomness goes through
  `RngService`, which CI enforces. The reason is in
  [`docs/rng/RNG_DESIGN.md`](docs/rng/RNG_DESIGN.md).
- See [`game/CLAUDE.md`](game/CLAUDE.md) for scene, autoload and naming rules.

### User-visible strings

- Every user-visible string ships in all five locales in the same commit:
  English, Italian, Spanish, French, German. CI fails on a missing or empty
  translation. The game's strings live in three tables under
  `game/localization/` — interface, rules vocabulary, content — and a key may be
  declared in only one of them.
- Game content is JSON under `game/data/` and carries no prose: every
  player-visible string is a localisation key.
  `tools/scripts/check_content.py` enforces that, along with the schema,
  cross-references and numeric ranges.
- Rules terminology in Italian, Spanish, French and German follows the official
  localised editions of the System Reference Document. Do not machine-translate
  rules terms. See [`docs/i18n/LOCALIZATION.md`](docs/i18n/LOCALIZATION.md).
- UI work must account for accessibility, keyboard, mouse, touch, and adaptive
  phone and tablet layout.

## 6. Tests

Update automated coverage whenever behaviour changes, using the closest existing
test style:

| Code | Tests | Runs in |
| --- | --- | --- |
| `host-core/` | JUnit 5, `host-core/src/test/kotlin` | `CI / gradle` |
| `app/` | JUnit 5 unit tests, `app/src/test/kotlin` | `CI / gradle` |
| `game/` | GUT, `game/tests/unit` | `CI / godot` |

Instrumentation tests in `app/src/androidTest` exist but do **not** run in CI:
the application is `arm64-v8a` only and the hosted runners provide no matching
device. This gap is recorded in
[`docs/release/READINESS.md`](docs/release/READINESS.md).

## 7. Labels

Pull requests are labelled automatically from the paths they touch
(see [`.github/labeler.yml`](.github/labeler.yml)). The canonical label
taxonomy lives in [`tools/labels.yml`](tools/labels.yml); add a label there and
create it in the repository before referencing it from any workflow, otherwise
labelling silently fails.

## 8. Dependencies

- Add a dependency only with a stated reason, and only to
  `gradle/libs.versions.toml`.
- Dependabot proposes updates weekly. Patch and minor updates to development and
  CI tooling merge automatically; anything else — majors, and anything touching
  the Godot library, the Android Gradle plugin or the SDK — is reviewed by hand.
- Security overrides for vulnerable transitive build tooling belong in
  [`config/build-tool-security.versions`](config/build-tool-security.versions).
- A third-party GitHub Action is pinned to a full commit SHA, with the version
  in a trailing comment so Dependabot can still update it:
  `uses: owner/action@<40-hex-sha> # v1.2.3`. Resolve the SHA from the action's
  own repository, never from a fork. CI enforces this, and the reasoning is in
  [the threat model](docs/architecture/THREAT_MODEL.md).
- When a shipped dependency or a licensing obligation changes, update
  [`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md) in the same pull request.

## 9. Security

Never commit credentials, signing keys or keystores, and never let them reach
logs, artifacts or pull request text. Report vulnerabilities privately through
the process in [`SECURITY.md`](SECURITY.md) — not in an issue or a pull request.
